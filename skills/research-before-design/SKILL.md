## 使う場面と使わない場面

使うのは、判断の答えが外部の情報で変わるとき。

- 新しいツール・ライブラリ・サービスを選ぶ、または比較する
- 外部APIや設定ファイルの仕様に依存する判断をする
- 「できない」「非対応」「そのAPIは存在しない」と言おうとしている
- 自作のユーティリティや仕組みを書こうとしている
- 不慣れな領域で、一般知識から推論して案を組もうとしている
- やり直しが難しい構成を決める（基盤の採用、データモデル、インフラ）

使わないのは、外部を調べても判断が変わらないとき。

- 既存コードを読めば決まる変更（名前の変更、既存パターンに沿った追加、バグ修正）
- 好みや文脈で決まる判断（文言、ファイルの置き場所）
- 採用済みの技術の範囲内での設定変更
- 導入済みツールの仕様確認で、手元の `--help`・man・インストール済みのソースを1〜2回見れば済むもの
- ユーザーが方式・ツール・設定まで指定していて、自分が選ぶ余地がないもの。ただし、指定された方式が成立するか疑わしいとき（例: 指定された機能がプロジェクトのバージョンで使えるか未確認）や、「できない」と返そうとしているときは使う

迷うときは「外部を調べた結果で、この判断は変わりうるか」で決める。

使わない場合は、以降の手順と報告の形式は不要。外部の仕様に基づく主張には、確認した手段（手元の資料、または公式ドキュメント1〜2ページ）とバージョンを1行添える。確認していないもの、プロジェクトのバージョンが分からないものはその旨を書く。

## 1. 問いを立てる

調査を始める前に、次を短く書き出す。

- 何を決めようとしているか
- 何が分かると選択が変わるか。これを調査の問いにする
- 問いの種類。(a) 仕様の確認で済むもの（この機能はあるか、このバージョンで使えるか） (b) 複数の解法を比較するもの（この課題を他はどう解いているか）
- 自分の制約（環境、バージョン、運用条件、既存の採用技術）。バージョンや設定は推測せず、`go.mod`・lockfile・ツールのバージョン指定など、プロジェクトのファイルで確認して書く。確認できないものは未確認と書く
- (b) を含むなら候補の範囲。調べる候補と、調べずに外す候補を理由つきで分ける。外す理由が一般知識による判断なら、その旨を書く

(a) だけなら軽い調査、(b) を含むなら本格調査になる。軽い調査は、一次資料による仕様確認と、代替手段の簡単な確認までにとどめる。どちらもsubagentに委譲する。

## 2. subagentに委譲する

調査は読み取り専用のsubagent 1つに委譲し、親の会話では外部の検索・取得を行わない。プロジェクトのファイルや手元のコマンドでの確認は親が行う。subagentには調査だけをさせ、設計の選択は親が行う。

| ホスト | 起動方法 |
|---|---|
| Claude Code | Agentツールでgeneral-purposeを起動し、modelにsonnetを明示する |
| Codex | spawn_agentで起動する |

subagentには次を渡す。

- 1で書いた判断の内容・問い・制約
- 調べる対象。可否に直結する仕様は公式ドキュメント・リリースノート・ソースコード。解法はOSS・技術記事・公開された設計
- 調べ方の要件
  - 一次資料を優先し、主張ごとに出典URL・対象バージョン・確認日を付ける
  - プロジェクトのバージョンに対応する資料を見る（バージョン付きのドキュメント、該当タグのソース、CHANGELOG）。最新版の資料しか見つからないときは、プロジェクトのバージョンとの差をCHANGELOGなどで確認し、その旨を書く
  - (b) で既存の解法を比較するときは、READMEやドキュメントだけでなく実装とテストを確認する。ドキュメントだけで「できる」と判断しない
  - 最初に見つけた案を裏付ける情報だけでなく、不利な制約や反証も探す
  - 見つからなかったものは「今回の探索では確認できなかった」と書く。「存在しない」とは書かない
  - 使えなかった検索手段（ツールが無い、アクセスできない）を明記する
- 3の報告形式

## 3. 報告の形式

subagentの報告も、親が設計案に含める調査結果も、この形式にする。

### 確認した仕様
- 主張 / 出典URL / 対象バージョン / 確認日
- 共通する確認日は見出しでまとめて書いてよい
- 対象バージョンがプロジェクトのバージョンと違うときはその旨を書く。バージョンのないサービスは、提供形態（例: github.com）と確認日で代える

### 検討した既存の解法
- 名称 / 何をどう解いているか / 成立の前提 / 自分の制約に適合する点・しない点
- subagentは採否を書かない。採否は親が5で決める
- (a) の軽い調査では、確認した代替手段を1行ずつ書けばよい。代替手段を確認していなければ「対象外」と書く

### 未確認・不一致
- 「未確認」「資料間で不一致」「非対応を確認」を区別して書く
- 使えなかった検索手段

### 判断への影響
- この結果でどの選択肢が残り、どれが消えたか

## 4. 完了を判定する

検索回数や記事数では判定しない。次を満たしたら設計へ進む。

- 判断を左右する仕様について、対象バージョン・確認日・一次資料を示せる
- 有力な既存の解法を確認し、自分の制約に対する採否の理由を言える。候補が少ないなら探索範囲を示し、比較表を埋めるために水増ししない
- 推薦に不利な制約や反証を確認している
- 残った未確認事項を、次のどれかに振り分けて対処している。複数に当てはまるときは上から順に当てはめる
  - どの選択肢でも結論が変わらないもの: 未確認として残し、先へ進む
  - 外部の資料で解消できるもの: 問いを絞って、同じ形式で追加調査を依頼する
  - ユーザーの環境や意思でしか決まらないもの: 調査は追加せず、仮定と影響範囲を明示してユーザーに確認する

## 5. 設計へ渡す

親は候補を制約と突き合わせ、それぞれを採用・拡張・組み合わせ・自作・不採用のどれにするか、理由とともに決める。

ユーザーへの回答は、結論と提案を先に置き、3の形式の調査結果を続ける。subagentの報告はそのまま転記してよい。「判断への影響」と採否は親の判断として書く。

- 調べる前の見立て（「できない」など）が覆ったら、回答の冒頭で、当初の見立てが誤りだったことと、覆した一次資料を示す
- 既存の解法を直接採用しない場合も、その設計から取り入れる点を書く
- 「できない」「非対応」と結論する場合は、対象バージョンと一次資料を示す
